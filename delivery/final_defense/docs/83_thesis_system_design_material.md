# E-Review Agent 系统设计章节材料

## 1. 系统设计目标

E-Review Agent 面向电商平台商品评价治理场景，目标是在保留传统商城浏览、下单、评价和后台管理能力的基础上，引入智能体协同机制，对图文评价进行自动分析、风险识别、运营建议生成和人工处理闭环管理。系统设计强调三个方面：第一，前台用户评价能够进入真实业务数据表，而不是停留在孤立演示数据；第二，后台智能体巡检能够持续发现待分析评价并生成可追踪结果；第三，答辩演示、论文说明和系统测试均能够稳定复现。

本系统的建设范围定位为毕业设计原型系统。系统不接入真实支付、真实物流和真实退款流程，不强制依赖外部大模型 API Key，也不依赖外部向量数据库。演示支付和演示发货仅用于推进订单状态，帮助完整展示“用户评价进入智能体治理流程”的业务闭环。

## 2. 总体架构设计

系统采用前后台分离和多服务协同架构，主要由 H5 用户端、管理后台、Spring Boot 后端服务、FastAPI AI 服务和 MySQL 数据库组成。

H5 用户端负责商品浏览、登录、下单、演示支付、演示发货、确认收货和发布图文评价。管理后台负责商品评论管理、AI 工作台、智能体巡检、风险评论中心、运营处理中心、执行追踪、工具注册、RAG 质量评估和 AgentOps 运行分析。Spring Boot 后端拆分为用户端接口和管理端接口，分别承载前台业务请求和后台治理请求。FastAPI AI 服务提供评价分析、风险判断和规则化建议能力。MySQL 保存商城基础数据、真实评论、AI 分析结果、风险任务、运营处理记录、智能体运行轨迹和质量评估数据。

该架构使传统电商交易链路和 AI Agent 治理链路相互衔接，又保持服务边界清晰。用户端产生评价，后台智能体巡检评价，AI 服务返回分析结果，管理端展示任务与处理建议，最终形成可解释、可追踪、可复验的闭环。

## 3. 前后台结构设计

前台 H5 采用 Vue 2、Vant、Vue Router、Vuex 和 Axios 实现，面向普通用户提供移动端体验。其核心页面包括首页、商品列表、商品详情、订单提交、支付页、订单列表和评价提交页。系统在支付和发货位置加入演示模式提示，明确说明不调用真实支付和真实物流能力。

后台管理端采用 Vue 2 和 Element UI 实现，面向管理员、运营人员和答辩演示人员。后台围绕 AI 工作台组织功能入口，包括 AI Dashboard、AI 评价分析、商品评论一键分析、模拟评论提交、Agent 巡检中心、风险评论中心、运营处理中心、Agent Trace、Replay 对比、工具注册中心、工具协议清单、工具结构校验、案例知识库、RAG 质量评估、AgentOps 趋势、安全护栏和记忆中心。

前后台通过统一请求封装访问后端接口。后台请求由 Shiro 和管理端鉴权控制，用户端请求由用户登录 token 控制。系统未绕过原有权限机制，演示接口也以清晰的 `ai-demo` 命名标识边界。

## 4. AI 服务结构设计

AI 服务采用 FastAPI 实现，主要提供健康检查和评价分析接口。评价分析结果包含情感倾向、风险等级、置信度、摘要、证据和运营建议。当前实现以规则和 Mock 能力为主，适合毕业设计稳定演示和测试复现。

AI 服务与 Java 后端通过 HTTP 调用连接。后端负责从真实评论或演示评论中组装分析请求，AI 服务返回结构化结果后，后端将其保存到分析结果表，并在达到风险规则时生成风险任务。该设计将 AI 推理能力与业务落库逻辑分离，便于后续替换为真实模型或进一步扩展。

## 5. 数据库核心表设计

系统复用原商城核心表，包括商品表、货品表、订单表、订单商品表和评论表。其中 `litemall_comment` 是真实商品评价进入智能体治理流程的关键入口。

AI 治理相关表主要包括：

| 表名 | 作用 |
| --- | --- |
| `litemall_review_ai_analysis` | 保存评论 AI 分析结果 |
| `litemall_ai_review_risk_task` | 保存高风险评论治理任务 |
| `litemall_ai_operation_log` | 保存运营处理记录 |
| `litemall_ai_patrol_log` | 保存智能体巡检日志 |
| `litemall_ai_agent_run` | 保存智能体运行记录 |
| `litemall_ai_agent_step` | 保存智能体执行步骤 |
| `litemall_ai_agent_feedback` | 保存人工反馈与评价 |
| `litemall_ai_tool_registry` | 保存工具注册信息 |
| `litemall_ai_memory_profile` | 保存记忆画像 |
| `litemall_ai_guardrail_event` | 保存安全护栏事件 |

分析结果和风险任务通过 `source_type` 和 `source_id` 区分来源，包括真实商品评价、后台模拟评价和手动输入等。该设计避免重复分析同一评价，也让 Dashboard、风险中心和运营中心可以统一统计不同来源的数据。

## 6. 智能体运行机制设计

智能体巡检机制由定时任务和手动巡检入口组成。巡检服务按照配置扫描待分析数据源，默认保留后台模拟评论扫描，同时支持真实商品评价扫描。巡检过程中，系统会检查评论是否已经存在分析结果，避免重复调用 AI 服务和重复生成风险任务。

巡检流程包括：读取待分析评价、构造 AI 请求、调用 AI 服务、保存分析结果、按规则判断是否生成风险任务、记录巡检日志。若分析失败，系统记录失败原因并继续处理下一条数据，避免单条异常阻断整批巡检。

## 7. 工具协议化设计

系统在 v1.2 阶段增强了工具协议化能力。工具注册中心保存工具名称、输入输出结构、审批策略、风险等级和启停状态。工具协议清单以 OpenAPI 风格结构描述工具能力，本地 MCP 风格描述只表示本地 JSON 工具定义，不表示接入外部 MCP 服务。

工具结构校验用于检查工具定义是否具备必要字段、输入输出结构是否完整、风险等级是否明确。该设计使智能体能力从散落代码逐步转向可注册、可审计和可验证的工具资产。

## 8. RAG 质量增强设计

系统设计了案例知识库和 RAG 质量评估模块，用于辅助运营建议生成和质量分析。案例知识库保存典型评论风险样本、处理建议和适用场景。RAG 质量评估关注召回命中、空召回、错误召回、引用质量和建议可用性。

当前阶段的 RAG 能力以本地规则、案例数据和质量评估为主，不依赖外部向量数据库。该设计既能展示检索增强思想，也能保持答辩现场的稳定性和可复验性。

## 9. 安全护栏与人工反馈设计

安全护栏用于记录高风险工具调用、异常输入、敏感内容和策略阻断事件。人工反馈用于让运营人员对 AI 分析结果进行采纳、误报、风险等级偏高、风险等级偏低、建议不适用等反馈。反馈结果可以反向用于评估智能体建议质量。

系统没有将 AI 判断作为最终业务处理结果，而是采用“AI 识别 + 人工确认 + 运营闭环”的人机协同方式。该方式更符合电商评价治理场景的风险控制要求，也便于论文论证系统的可解释性和可控性。

## 10. 小结

E-Review Agent 的系统设计以真实评论闭环、智能体巡检、风险任务治理和答辩稳定演示为主线。系统在保留传统商城业务结构的基础上，引入 AI 分析、Agent 运行记录、工具协议化、RAG 质量评估和安全护栏机制，形成了适合毕业设计展示和论文撰写的完整原型系统。
