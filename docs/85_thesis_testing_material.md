# E-Review Agent 系统测试章节材料

## v1.4 产品体验回归测试补充

v1.4 新增 e-review-ux-refinement-check.ps1，用于检查 5 个 AI 工作台一级入口、旧路由兼容、首页主流程按钮、中文文案和页面可见异常文本。该脚本同时可联动 full-ui-flow 和 final-acceptance，保证产品体验收口不破坏 H5 真实评价闭环和后台最终验收。

浏览器回归重点包括：智能治理首页、评论治理流程、运行观测与评估、知识增强与质量、平台治理设置、H5 商品详情、H5 支付页和 H5 评价提交页。测试原则是不伪造生产能力，不接入真实支付、物流、退款或外部向量数据库。

## 1. 测试目标

系统测试目标是验证 E-Review Agent 在毕业设计答辩场景下具备可运行、可演示、可复验的质量状态。测试不仅覆盖 AI 工作台，还覆盖 H5 用户端、管理后台、后端接口、AI 服务、数据库、脚本工具和文档交付材料。

测试重点包括：服务是否能够启动，核心接口是否返回正常结果，前后台闭环是否完整，智能体巡检是否能处理真实评论，风险中心和运营中心是否联动，文档和脚本是否存在乱码、外链、私密路径和夸大表述。

## 2. 测试范围

测试范围包括以下模块：

| 模块 | 测试内容 |
| --- | --- |
| H5 用户端 | 首页、商品详情、订单提交、演示支付、演示发货、确认收货、评价提交 |
| 管理后台 | AI Dashboard、商品评论、Agent 巡检、风险中心、运营中心、Trace、Replay、工具与质量模块 |
| wx-api | 用户登录、商品、订单、演示支付、演示发货、评价提交 |
| admin-api | Dashboard、评论分析、巡检、风险任务、运营处理、工具协议、质量评估 |
| AI 服务 | 健康检查、评论分析、规则化风险结果 |
| 数据库 | 核心表、AI 分析表、风险任务表、运营日志表、Agent 运行表 |
| 文档材料 | 编码、链接、中文用语、安全卫生、交付索引 |
| 脚本工具 | 一键启动、检查、备份、恢复、演示数据重置、最终验收 |

## 3. 单元测试

AI 服务使用 `python -m pytest` 执行单元测试，验证健康检查、分析接口、规则模型和异常输入处理。单元测试的作用是保证 AI 服务内部逻辑在不依赖前后端页面的情况下可以独立验证。

后端 Java 项目通过 Maven 构建完成基础编译检查。当前阶段使用 `mvn -DskipTests package` 作为封版构建门禁，重点验证多模块依赖、Controller、Service、Mapper、配置文件和新增类是否能够通过编译。

## 4. 前端构建测试

管理后台和 H5 用户端分别执行生产构建。管理后台执行 `npm run build:prod`，H5 用户端也执行对应构建命令。构建测试用于发现 Vue 模板语法错误、未导入变量、API 引用错误、样式编译问题和依赖缺失问题。

前端构建通过后，结合浏览器手工检查或脚本访问检查，进一步验证页面是否可以打开、接口是否可访问、空状态和错误提示是否合理。

## 5. 服务健康检查

服务健康检查覆盖五类服务：

| 服务 | 端口 | 检查内容 |
| --- | --- | --- |
| AI 服务 | 8008 | `/api/v1/health` |
| wx-api | 8080 | `/wx/home/index` |
| admin-api | 8083 | Dashboard 和 AI 接口 |
| H5 用户端 | 6255 | 首页 HTTP 状态 |
| 管理后台 | 9527 | 首页 HTTP 状态 |

`e-review-check-all.ps1` 汇总检查端口监听、HTTP 状态、Dashboard 统计、风险任务数量和关键接口状态，输出 `CHECK_ALL_PASS` 作为基础服务可用证据。

## 6. 全菜单与接口测试

后台全菜单接口测试用于验证管理后台核心模块不因参数为空、权限异常或接口路径错误导致阻断。测试覆盖 Dashboard、商城基础模块、商品管理、订单管理、用户管理、评论管理、系统管理和 AI 工作台相关接口。

该类测试关注两个结果：HTTP 层是否返回可访问状态，业务层是否返回 `errno=0` 或明确的权限提示。测试不通过简单隐藏错误实现，而是要求接口返回结构清晰、错误原因可定位。

## 7. Full UI Flow 端到端测试

Full UI Flow 是系统最重要的端到端测试之一。它从 H5 用户端开始，覆盖用户登录、选择固定演示商品、下单、演示支付、演示发货、确认收货、提交评价，再进入管理后台检查 Dashboard、商品评论、Agent 巡检、风险中心、运营处理、Agent Trace、Agent Eval 和配置中心。

该测试证明系统不只是单个页面可用，而是从顾客端到管理员端形成一次完整闭环。脚本成功时输出 `FULL_UI_FLOW_PASS` 和 `CUSTOMER_ADMIN_END_TO_END_PASS`。

## 8. Final Acceptance 测试

Final Acceptance 是封版级验收脚本，整合演示商品种子、后台全菜单 API 检查、后台 API 矩阵、文档链接检查、Smoke 测试、客户闭环测试、Agent 框架检查、Full UI Flow 和数据库一致性检查。

该脚本输出 `FINAL_ACCEPTANCE_PASS`，表示当前系统满足主要演示、接口和数据一致性要求。若脚本失败，应根据失败模块回到对应服务、数据库或页面进行最小修复，而不是跳过失败项。

## 9. RAG Quality 与 Tool Schema 测试

RAG Quality 测试用于验证案例知识库、召回结果、质量指标和低质量样本记录是否存在并可读取。Tool Schema 测试用于验证工具协议清单和工具注册结构是否完整。二者分别输出 `RAG_QUALITY_CHECK_PASS` 和 `TOOL_SCHEMA_CHECK_PASS`。

这些测试支撑论文中关于“检索增强质量评估”和“工具协议化”的章节说明，使相关能力不只停留在页面展示，而有脚本化证据。

## 10. Security Hygiene 与 Error Message 测试

Security Hygiene 测试检查交付材料和源码中是否出现本地数据库密码、私密用户路径、file URI、OpenAI Key 字面量、外部能力误称和生产能力夸大表述。Error Message 测试检查用户可见文本中是否存在乱码、粗糙内部错误、私密路径和不适合展示的错误信息。

两个脚本分别输出 `SECURITY_HYGIENE_CHECK_PASS` 和 `ERROR_MESSAGE_CHECK_PASS`。这类测试支撑毕业设计交付材料的规范性，也降低答辩展示中出现敏感信息或误导性表述的风险。

## 11. 浏览器手工回归测试

浏览器手工回归测试使用系统 Chrome 打开真实页面，并在可用时补充 Edge 检查。测试记录 H5 首页、商品详情、订单相关页面、评价提交页面，以及后台 AI 工作台、商品评论、巡检中心、风险中心、运营中心、工具和质量模块是否能正常打开。

浏览器回归报告不替代自动化测试，而是提供答辩前的真实浏览器证据。其结论写入 `docs/89_final_browser_regression_report.md`。

## 12. 测试结论写法

论文中建议将测试结果表述为：系统通过了单元测试、构建测试、服务健康检查、核心接口检查、端到端流程测试、最终验收脚本和浏览器回归检查。若某些能力仍为演示模式或规则模型，应明确说明其边界，例如不接真实支付、不接真实物流、不依赖外部向量数据库。

测试结论应以实际脚本输出和报告记录为依据，不伪造测试结果，不将未验证能力写成已完成能力。
